async fn serve_feed(socket: UdpSocket, feed: Feed, ingestor: Arc<Ingestor>) {
    // Max UDP payload; datagrams arrive whole or not at all.
    let mut buf = vec![0u8; 65535];
    loop {
        let (len, src) = match socket.recv_from(&mut buf).await {
            Ok(v) => v,
            Err(e) => {
                error!(feed = %feed.label, error = %e, "udp recv failed");
                tokio::time::sleep(std::time::Duration::from_millis(100)).await;
                continue;
            }
        };
        ingestor.ingest(&feed.label, &src, &buf[..len]).await;
    }
}

octo-pod

An edge gateway between sensors and a shared fabric.

It runs on one small computer where sensors live, takes in their feeds, records and audits them locally, and releases only what you choose onto a shared Zenoh network that other sites share.

What it is

A sensor speaks its own wire format on its own network and has no place on a shared fabric; a shared fabric should not reach back into a sensor's network. octo-pod is the boundary between the two. One pod serves one site; a larger deployment is many pods, each releasing into the same fabric and each governed on its own.

Ingress

Feeds come in through arms

An ingress arm takes a UDP or TCP sensor feed, or a Zenoh-native publisher connects directly. Each arm gets its own certificate and a narrow set of keys it may publish.

Release

Nothing crosses that you did not declare

Capture stays local until you release it. The fabric carries only the feeds a pod releases, under the names and to the audiences its operator declared. An optional pod firewall limits traffic to the connections you named.

Egress

And out to receivers

An egress arm delivers released fabric data to a receiver over UDP, TCP or SAPIENT, or publishes into a partner's own Zenoh router with the credentials the partner issued.

Declare, check, apply

Every change edits the pod's declaration; nothing on the running pod changes until you apply. check shows what apply would change and changes nothing. Between applies the pod renews its own certificates and repairs supported service faults, without changing your declaration.

What crosses, and how

The functions the pod's configuration and CLI expose. Byte ingress and byte egress preserve the payload format. Local capture does not provide durable store-and-forward delivery.

Deploy a pod

The pod: Ubuntu 24.04, amd64 or arm64, with SSH and sudo. The laptop: Git, an authenticated GitHub CLI and cosign. A disconnected site follows the air-gapped installation. Examples use 192.0.2.10 for the pod and 192.0.2.30 for a sensor.

Stop on any failed command. For an existing pod, use the upgrade guide.

  1. Install from your laptop

    $ tools/install-to-pod.sh operator@192.0.2.10 \
    --version 0.5.0 --with-images
$ ssh operator@192.0.2.10

  2. Prepare the pod

    $ sudo octo-pod bootstrap --tags base,verification,clock,netbird
$ sudo octo-pod bootstrap -e bootstrap_mode=airgap \
    -e image_mirror=localhost:5000 --tags images

  3. Initialize, or join a mesh

    $ sudo octo-pod init --pod pod1
$ sudo octo-pod set-mesh --mirror localhost:5000

    To join a mesh instead, use join --setup-key-file … --mgmt … --pod pod1; see mesh enrollment.

  4. Add a sensor and start capture

    $ sudo octo-pod add-arm sensor1 --udp 48021 \
    --from 192.0.2.30 --bind 192.0.2.10
$ sudo octo-pod check
$ sudo octo-pod apply

  5. Verify

    $ sudo octo-pod verify
$ sudo octo-pod status
$ sudo octo-pod verify-flowing

    After the sensor sends data, verify-flowing must pass and the received and forwarded counters must increase.
